## 0. INPUT BLOCK — REGLA ABSOLUTA

`INPUT_RAW` se conserva byte-a-byte como fuente de verdad. Ningún parser, LLM, router, normalizador ni agente puede sustituirlo. Toda interpretación vive en un sidecar derivado con `sha256(INPUT_RAW)` y trazabilidad hacia el original.

Cadena obligatoria:

`INPUT_RAW → INPUT_LOCK → DERIVED_ANALYSIS → RESEARCH_DAG → EVIDENCE → CONTEXT_PACKAGE → LLM PRINCIPAL`

La LLM de enfoque puede proponer preguntas, subproblemas y búsquedas, pero NO puede: mutar `INPUT_RAW`, inventar evidencia, declarar PASS, ocultar contradicciones ni cerrar una investigación.

## 3. CONTRATO DE 3 PASOS — NO EXPANDIR

### Paso 1 — ANOTAR + ARQUITECTURA
Registrar cada decisión, componente, fuente, tarea y estado. Mantener el INPUT literal. Toda IA escribe en su propio registro dentro de Craxy Wall y actualiza `STATE.json` sin eliminar evidencia previa.

### Paso 2 — DESCARGAR + EXTRAER + COPIAR/MOVER
Usar los motores canónicos existentes en el repositorio. Los motores son inmutables. Se crean múltiples instancias/jobs con entradas, colas y estados separados; no forks reescritos del motor.

Motores canónicos:
- `motor_1_extract_only.py` — extracción ZIP verificada.
- `motor_2_queue_download_extract.py` — cola persistente de adquisición/extracción.
- `hf_download_extract_engine.py` — adquisición Git, bundle ZIP, reconstrucción, extracción, tree-hash y publicación/read-back.
- `motor_3_copy_batches.py` — copia por lotes con hash/read-back.
- `motor_copy_root_to_repo.py` — copia estricta de la raíz canónica de motores.
- `motor_4_move_batches.py` — movimiento por lotes con verificación.

Regla: `VERIFIED_CLOSED` sólo con `pending=0`, `failed=0` y read-back cuando exista publicación.

### Paso 3 — CABLEAR + PODA MÍNIMA + CODE FALTANTE + TEST
No rediseñar componentes descargados. Cablear mediante adaptadores y contratos estables. Podar únicamente si una incompatibilidad demostrable lo exige. Generar código nuevo sólo para glue/adapters/microkernels faltantes. Ejecutar tests y registrar evidencia.

## 4. DEFINICIÓN DEL SISTEMA

**Wanted Shark Web / Shack imput** es una capa universal de inteligencia pre-LLM que convierte un INPUT pequeño, vago o grande en un paquete investigado, trazable y enfocado antes de que la LLM principal razone.

No es sólo RAG. Conecta cinco universos:
1. KNOWLEDGE UNIVERSE — información/evidencia.
2. CODE UNIVERSE — repositorios, símbolos, funciones, imports, callers/callees.
3. SKILL UNIVERSE — procedimientos cargables bajo demanda.
4. TOOL UNIVERSE — herramientas y capacidades ejecutables.
5. CAPABILITY GRAPH — relación entre necesidad, conocimiento, code, skill y tool.

## 6. DETERMINISMO

Modo D0 STRICT:
- raw input inmutable + SHA-256;
- reglas, regex, diccionarios, gramáticas;
- árbol/grafo de dependencias;
- query templates;
- snapshot de fuentes;
- exact search/BM25;
- RRF fijo;
- scoring fijo;
- Evidence Ledger;
- coverage thresholds;
- canonical JSON.

Modo D1 FROZEN NEURAL opcional:
- embeddings/rerankers con versión y hash congelados;
- mismos snapshots e inputs;
- runtime fijado.

Modo D2 FOCUS AI:
- sólo para enfoque, preguntas y descubrimiento de nuevos gaps;
- nunca autoridad de evidencia ni PASS.

## 7. SHARK FOCUS + PREGUNTAS 3–12

La IA de enfoque trabaja en dos momentos:
- Focus A: antes de investigar, detecta intención, interpretaciones, huecos y preguntas.
- Focus B: después de la primera evidencia, identifica nuevas contradicciones/gaps y solicita búsquedas delta.

Activación sugerida por `FOCUS_SCORE = ambiguity + domains + unresolved_entities + missing_constraints + conflicts + complexity + consequence_of_error`.

Rangos:
- claro/simple: 0–3 preguntas;
- moderado: 3–5;
- grande: 6–9;
- muy vago/complejo: 10–12;
- contradicción nueva: +1–3 preguntas delta.

El PRESEARCH no espera al usuario: comienza con los hechos/entidades no ambiguos mientras el usuario responde.

## 8. ROUTER DE ROLES / DOMINIOS

Multi-role, no persona única. Ejemplos:
- programación → software architect + developer;
- arquitectura → systems architect;
- UI/UX → product/UI designer;
- vídeo → director/video engineer;
- gráfico/arte → graphic designer/art researcher;
- cocina → chef/food researcher;
- ciencia → research scientist;
- noticias → news researcher + freshness verifier;
- país → country specialist;
- idioma → language specialist;
- cultura → cultural researcher;
- religión → religion research lens, sin inferir religión del usuario.

Cada rol modifica fuentes, vocabulario, facetas y criterios de autoridad. Se permiten múltiples roles simultáneos.

## 9. DEV COMMUNITY BOOSTER

Registry fijo de más de 50 superficies. No se consultan todas siempre: el router activa un subconjunto y amplía si el coverage gate falla. Community evidence nunca equivale a primary-source evidence.

El registry ejecutable vive en `➡️📂 shart imput code Run/community_registry.json`.

## 10. GITHUB / CODE SEARCH BOOSTER

Para programación se activa automáticamente:
`repo → README/docs → symbols → code search → issues → PR → releases → commits → tests → examples → license → activity → alternatives`.

### Code Pointer RAG
No meter repos completos en el prompt. Indexar:
`repo + commit + path + symbol + signature + lines + callers + callees + hash`.

La LLM recibe referencias. Sólo al pedir `read_symbol(ref)` se recupera el cuerpo necesario.

Stack principal de code intelligence:
Tree-sitter + Aider RepoMap pattern + SCIP + Zoekt + OpenGrok + ast-grep + Semgrep + Pyright + Jedi + Universal Ctags + ripgrep.

## 11. SKILL POINTER RAG

Los skills se registran con:
`skill_id, capabilities, domain, repo, commit/ref, subfolder, version, dependencies, allowed_tools, trust, license, tests`.

La LLM carga metadata corta; el contenido `SKILL.md` se recupera sólo bajo demanda. Fuentes prioritarias: Anthropic Skills, Hugging Face Skills, Microsoft Skills, OpenAI Skills, GitHub Awesome Copilot, ToolHive Catalog y registries auditables.

## 12. TOOL/CAPABILITY FINDER

Flujo:
`required capability → local connected tools → MCP registries → GitHub/HF/direct APIs → shortlist → security/permission filter → 3–8 tools → LLM`.

Nunca exponer miles de tools a la LLM. Descubrimiento proactivo sí; instalación/ejecución de código no confiable sin gate, no.

Ficha de herramienta:
`tool_id, capabilities, interface, inputs, outputs, auth, platform, destructive, read_only, idempotent, source, version, commit, docs, examples, security_score, tested`.

## 13. BUSCADORES TIPO PERPLEXITY / DEEP RESEARCH

Se integran varios sistemas y se extraen mecanismos, no se obliga a depender de uno:
SearXNG, Vane, Morphic, GPT Researcher, Local Deep Researcher, Open Deep Research, MindSearch, DeerFlow, Khoj, Firecrawl, Crawl4AI, Browser Use, Playwright MCP.

Wanted Shark mantiene su Core determinista y usa estos componentes como fuentes/adaptadores/mecanismos.

## 14. YOUTUBE RESEARCH KERNEL

Cadena preferida:
`YouTube URL/search → metadata → captions/subtitles → transcript normalize → timestamps → evidence chunks`.

Fallback si no hay captions:
`audio → Whisper/faster-whisper/whisper.cpp → transcript → timestamped evidence`.

Componentes: yt-dlp, youtube-transcript-api, yt-transcript, faster-whisper, whisper.cpp, WhisperX, Whisper.

## 15. INPUT LITERAL KERNEL

Implementación local inicial: `shark_input_lock.py`.

Reglas:
- jamás trim/normalizar antes de guardar `raw`;
- hash del UTF-8 original;
- toda extracción es sidecar;
- `assert_literal_integrity()` antes de compilar contexto;
- parser estructural opcional con Pydantic, JSON Schema, Lark, pyparsing, msgspec, Marshmallow, ANTLR4;
- si una LLM produce estructura, Outlines/Guidance pueden restringir el formato, pero jamás reemplazar el raw input.

## 17. MOTORES FÍSICOS DE ARCHIVOS

No se reescriben. El workflow crea jobs independientes que apuntan a los mismos binarios canónicos y pasan variables explícitas.

Patrón:
`same immutable motor × N queue/state/source/destination instances`.

Esto satisface la idea de varios micro-motores que siempre hacen el mismo trabajo sin duplicar/adulterar código.

## 18. MEMORIA DE BÚSQUEDA

Archivo humano inicial: `➡️📂 shart imput code Run/memoria búsqueda.md`.

Debe acumular:
- queries;
- fuentes visitadas;
- snapshots/hashes;
- evidencia aceptada/rechazada;
- contradicciones;
- gaps;
- roles activados;
- code refs;
- skills/tools descubiertos;
- decisiones del router;
- pendientes.

La memoria nunca sustituye al Evidence Ledger ni al INPUT_RAW.

## 19. CRAXY WALL — MULTIAGENTE

`STATE.json` es pizarra compartida. Cada agente tiene log propio. Regla: leer STATE + handoff antes de escribir. Nunca borrar el trabajo de otro agente. Actualizar revision y registrar paths tocados. ChatGPT/Sol, Astra y Grok trabajan por nodos separados.

Paquete final:

## 21. PRINCIPIO DE CIERRE

La LLM principal razona sólo después del Context Compiler. El Core puede continuar investigación delta si Focus B o el quality gate detectan gaps. Ningún agente declara DONE sólo por narración: se exige evidencia física/read-back/test según el método del repositorio.
